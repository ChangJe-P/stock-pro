# Google 로그인과 사용자별 가상계좌 전환 설계

## 1. 합의된 목표

주몽은 국내 주식 학습용 서비스다. 모든 계좌·현금·주문·손익은 가상이며, 실제 증권계좌·실제 돈·실제 주문·자동매매는 어떠한 화면·API·환경변수·외부 연동에도 만들지 않는다.

Google 로그인은 사용자의 학습 기록을 분리하기 위한 신원 확인 수단이다. 로그인한 Google 계정마다 가상계좌 하나와 그 계좌에 연결된 가상 원장·주문·포트폴리오를 갖는다. Google의 결제·금융 권한은 요청하지 않고, `openid`, `email`, `profile` 범위만 사용한다.

KRX 로그인은 저장용 일봉 가격 데이터를 얻기 위한 로컬 운영자 설정일 뿐이다. 실제 증권사 로그인과 무관하며, 사용자 입력·DB 저장·화면 표시 대상으로 삼지 않는다.

## 2. 현재 구조에서 반드시 고칠 점

현재 `VirtualAccount`는 `singleton` 제약을 갖고, 계좌·주문·대시보드 서비스가 첫 행을 조회한다. 또한 화면과 JSON API에 인증이 없고 일부 POST API는 CSRF 예외다. 이 구조에서는 여러 Google 사용자의 가상 기록을 안전하게 분리할 수 없다.

따라서 로그인 버튼만 추가하거나 탭 CSS만 바꾸는 방식은 사용하지 않는다. 먼저 계좌 소유권·세션·API 접근 제어를 도입하고, 그 다음 실제 기능이 있는 화면을 만든다.

## 3. 선택한 기술 방향

표준 Django 세션 인증과 Google OAuth를 사용한다. Google OAuth 흐름은 검증된 Django용 라이브러리(`django-allauth`의 Google provider)를 사용하며, 직접 OAuth 토큰 교환·쿠키 처리·사용자 생성 로직을 작성하지 않는다.

| 선택지 | 결과 | 판단 |
|---|---|---|
| Django 표준 세션 + 검증된 Google OAuth provider | 동일 origin의 Template·form·API와 자연스럽게 연결되고 보안 검증 범위가 작다. | 채택 |
| 브라우저 JavaScript에서 Google 토큰을 직접 처리 | 토큰 검증·갱신·CSRF·세션을 별도로 구현해야 한다. | 제외 |
| 로그인은 두되 단일 가상계좌 유지 | 사용자의 기록이 섞이며 Google 로그인의 목적이 없다. | 제외 |

새 환경변수는 루트 `.env`에만 둔다. 실제 값은 Git, `.env.example`, 로그, HTTP 응답, 인수인계 문서에 넣지 않는다.

| 변수 | 용도 |
|---|---|
| `GOOGLE_OAUTH_CLIENT_ID` | Google OAuth 클라이언트 식별자 |
| `GOOGLE_OAUTH_CLIENT_SECRET` | 서버 전용 OAuth 비밀값 |
| `INITIAL_OWNER_GOOGLE_EMAIL` | 기존 단일 가상계좌를 1회 연결할 수 있는 본인 Google 이메일 |

Google Cloud Console의 OAuth 동의 화면과 로컬 redirect URI 등록은 사용자가 직접 수행한다. Claude Code·Codex에 Client Secret을 전달하지 않는다.

## 4. 데이터 모델과 기존 기록 이전

### 사용자별 가상계좌

- Django의 기본 `User`와 `VirtualAccount`를 1:1로 연결한다.
- `VirtualAccount.singleton` 필드와 항상 참인 단일 계좌 제약을 제거한다.
- 새 가상계좌는 사용자가 로그인 후 명시적으로 `가상계좌 시작`을 선택할 때만 생성한다. 최초 가상 현금은 기존 정책 환경변수의 `10,000,000원` 스냅샷을 사용한다.
- `CashLedgerEntry`와 `VirtualBuyOrder`는 이미 `account_id`로 연결되어 있으므로, 계좌의 소유권을 기준으로 함께 분리한다. 원장·주문·가격 행을 삭제하거나 재작성하지 않는다.
- `DailyPrice`, `MarketDataCollectionRun`은 실제 시장의 공용 학습 데이터이므로 사용자별로 복제하지 않는다.

### 기존 단일 계좌 연결

현재 존재하는 단일 가상계좌는 migration 직후 소유자 없는 legacy 계좌로 잠시 남긴다. 임의의 첫 로그인 사용자에게 자동 연결하지 않는다.

1. `INITIAL_OWNER_GOOGLE_EMAIL`과 일치하는 Google 계정으로 로그인한 사람만 연결 화면을 볼 수 있다.
2. 그 화면에서 `기존 가상 학습 기록 연결`을 명시적으로 확인해야 한다.
3. 서버는 트랜잭션과 행 잠금으로 legacy 계좌가 아직 소유자 없는지 다시 확인한 뒤 그 사용자에게만 연결한다.
4. 연결이 끝난 뒤 같은 요청을 반복해도 계좌·원장·주문이 추가되거나 재설정되지 않는다.
5. 다른 Google 계정은 legacy 기록을 읽거나 연결할 수 없으며, 새 가상계좌를 명시적으로 시작할 수 있다.

실제 DB migration 전에는 Docker PostgreSQL 볼륨의 백업 절차와 legacy 데이터가 유지되는 migration 테스트를 준비한다. 데이터 초기화나 `docker compose down -v`는 이 작업에 포함하지 않는다.

## 5. 접근 제어와 외부 호출 경계

| 경로·기능 | 로그인 | 사용자 소유권 | 외부 호출 |
|---|---|---|---|
| `/health` | 불필요 | 해당 없음 | DB 확인만 |
| 대시보드·가상계좌·원장·주문 화면/API | 필수 | `request.user`의 계좌만 | 없음 |
| 가상 주문 생성·수동 체결 | 필수 | 해당 사용자의 주문만 | 저장된 일봉만 읽음 |
| 일봉 조회 | 로그인 필수 | 가격 데이터는 공용 읽기 전용 | 없음 |
| 일봉 수집 | 초기 소유자(운영자)만 | KRX 자격증명은 서버 `.env`에만 존재 | 기존 pykrx 단일 호출만 |

기존의 JSON POST 호환을 위한 `csrf_exempt`는 사용자 계좌·주문을 다루는 경로에서 제거한다. 동일 origin의 로그인 세션과 CSRF 보호를 사용한다. 기존 공개 API의 200 응답을 유지하는 것보다 다른 사용자의 가상 기록을 노출하지 않는 것이 우선이다.

가상계좌·주문·체결 코드에는 증권사 endpoint, 계좌번호, 결제수단, 실제 잔고 조회, 실제 주문 요청을 추가하지 않는다. Google OAuth와 pykrx 가격 수집 외에는 외부 요청을 만들지 않는다.

## 6. 화면 전환 순서

### T-010: 인증과 기록 소유권 기반

- Google 로그인·로그아웃, 로그인 전 안내 화면, 로그인 세션을 추가한다.
- 기존 가상계좌 연결 또는 새 가상계좌 시작 흐름을 추가한다.
- 기존 대시보드·데이터 준비 화면을 로그인 사용자 기준으로 바꾼다.
- 구현된 대시보드와 데이터 준비 화면만 navigation에 연결한다. 동작하지 않는 주문·내역·설정 탭은 만들지 않는다.

### T-011: 실제 기능이 있는 금융 앱 화면

- 대시보드, 데이터, 가상 주문, 거래 내역, 설정을 각각 별도 URL과 실제 데이터로 제공한다.
- 공통 상단 navigation, 현재 로그인 사용자 표시, 로그아웃, 반응형 금융 UI를 제공한다.
- 기존 T-004 주문 엔진을 사용자 소유권 범위에서 재사용한다. 새 실제 거래 기능은 만들지 않는다.
- 빈 카드, 가짜 차트, 준비 중 버튼, 작동하지 않는 탭을 만들지 않는다.

차트·관심종목·가상 매도·손실 한도 기록은 T-011 이후 별도 작업으로 분리한다.

## 7. 완료 검증 기준

T-010은 다음 증거가 모두 있을 때만 완료다.

1. 비로그인 사용자는 사용자 데이터 화면과 사용자 계좌·주문 API에 접근할 수 없다.
2. 서로 다른 두 Google 사용자는 상대방의 가상계좌·원장·주문·포트폴리오를 조회·생성·체결할 수 없다.
3. 기존 legacy 계좌는 허용된 본인 Google 이메일의 명시적 1회 확인으로만 연결되며, 계좌·원장·주문 데이터가 유지된다.
4. 새 사용자는 명시적으로 시작할 때만 `10,000,000원` 가상 현금의 계좌를 받는다.
5. 일봉 수집은 운영자만 실행할 수 있고 KRX ID·비밀번호는 응답·로그·DB·화면에 노출되지 않는다.
6. 주문 체결은 저장된 다음 거래일 시가만 사용하며 실제 증권사·결제·계좌 API 요청을 하지 않는다.
7. Django 검사, migration dry-run, 전체 테스트, 신규 인증·소유권·legacy migration·CSRF 테스트가 통과한다.

## 8. 제외 범위

- 실제 증권계좌·실제 돈·결제·실주문·자동매매·투자 자문
- 사용자 KRX 아이디·비밀번호 입력/저장, KRX 브라우저 자동 로그인, 쿠키·세션 파일 저장
- Google 외 로그인 제공처, 비밀번호 로그인, 다단계 권한 체계, 결제·구독
- 배포, HTTPS 운영 구성, Notion API, 차트·관심종목·뉴스·AI 추천
- 가상 매도·손실 한도·계좌 재설정·정책 변경
