# T-004 가상 매수 주문과 다음 거래일 시가 체결

## 목표

단일 로컬 가상계좌에서 학습용 **매수 주문**을 기록하고, 주문을 결정한 거래일보다 엄격히 뒤의 첫 저장 일봉 시가로 수동 체결할 수 있게 한다. 체결 금액·수수료·슬리피지·가격 출처를 보존하고, 현금 변화는 T-003의 추가 전용 현금 원장에 한 번만 기록한다.

이 작업의 핵심은 같은 날 종가를 확인한 뒤 같은 날 가격으로 체결하는 미래 데이터 누수를 막는 것이다. 실제 돈·실제 주문과는 무관하다.

## 이번 작업의 고정 결정

### 주문 범위

- T-004는 `buy`만 지원한다. 매도는 검증 가능한 보유 수량이 아직 없으므로 만들지 않는다.
- 주문 생성 요청의 `decision_trade_date`는 사용자가 장 마감 후 판단을 끝낸 거래일을 뜻한다. 서버가 현재 시각·장 시간·휴장일을 추정하지 않는다.
- 해당 종목·결정 거래일의 **비조정** 저장 일봉이 있어야 주문을 생성할 수 있다. 없으면 외부 수집을 시작하지 않고 명시적으로 실패한다.
- 체결은 예약 실행·스케줄러가 아니라 사용자가 호출하는 단일 주문 체결 API로만 시도한다.
- 주문 취소, 수정, 수량 변경, 현금 예약은 이번 작업에 넣지 않는다. 대기 주문은 실제 현금을 차감하지 않으며 체결 시점의 원장 합계 현금을 기준으로 판단한다.

### 체결 가격과 비용 규칙

1. `daily_prices`에서 `trade_date > decision_trade_date`인 행 중 가장 이른 거래일 한 행만 고른다.
2. 선택된 행은 비조정 가격이어야 하며, 그 `open_price`를 기준 시가로 쓴다. 같은 날 행 또는 종가는 체결에 사용하지 않는다.
3. T-003 계좌 스냅샷의 슬리피지를 매수자에게 불리하게 적용한다.

   ```text
   execution_price_krw = ceil(open_price * (10,000 + slippage_bps) / 10,000)
   gross_amount_krw = execution_price_krw * quantity
   fee_krw = ceil(gross_amount_krw * buy_fee_rate)
   cash_delta_krw = -(gross_amount_krw + fee_krw)
   ```

- 현금·가격·수량·수수료는 모두 KRW 정수(`bigint`)로 저장한다. 수수료 계산에는 `Decimal` 등 결정적 산술을 사용하며 금액 계산에 binary float를 쓰지 않는다.
- 현재 현금이 `gross_amount_krw + fee_krw`보다 작으면 주문은 `rejected_insufficient_cash`로 종료한다. 현금 원장 행은 만들지 않는다.
- 다음 거래일 시가가 아직 저장되지 않았으면 주문은 `pending`으로 그대로 두고 409 응답을 반환한다. 외부 가격 수집을 요청하지 않는다.

### 주문 상태

| 상태 | 의미 | 다시 체결 시도 |
|---|---|---|
| `pending` | 다음 거래일 시가를 아직 찾지 못한 매수 주문 | 가능 |
| `filled` | 다음 거래일 시가 기준으로 현금 원장까지 기록된 체결 | 기존 결과만 반환 |
| `rejected_insufficient_cash` | 체결 시점 현금 부족으로 끝난 주문 | 기존 결과만 반환 |

## 구현 범위

### 1. 저장 구조

기존 T-003 계좌·현금 원장과 T-002 일봉 테이블을 재사용한다. 새 의존성, 마이그레이션 프레임워크, 다중 사용자 모델을 추가하지 않는다.

- `virtual_buy_orders` 테이블을 추가한다.
  - DB 생성 주문 식별자, 계좌 식별자, 6자리 종목 코드, 양수 정수 수량, 결정 거래일, 생성 시각, 상태
  - 체결 시각·거래일, 기준 시가, 슬리피지 적용 체결가, 총 체결 금액, 수수료, 안전한 종료 사유
  - 선택한 가격 행의 데이터 출처, 비조정 여부, 수집 실행 식별자
  - `pending`, `filled`, `rejected_insufficient_cash` 외 상태는 DB 제약으로 막는다.
- `cash_ledger_entries`에 체결 주문 식별자를 연결할 수 있는 nullable 컬럼을 재실행 안전하게 추가한다.
  - 체결 주문 하나당 현금 원장 행은 최대 한 개가 되도록 DB 유일 제약 또는 동등한 유일 인덱스를 둔다.
  - 체결 현금 원장 유형은 `buy_execution`이며 금액은 음수 `cash_delta_krw`다.
  - T-003의 `opening_balance` 행과 기존 원장 데이터는 변경하지 않는다.
- 체결 트랜잭션에서 가상계좌 행을 잠가 현금 합계 확인·주문 상태 갱신·현금 원장 추가를 직렬화한다. 동시에 두 주문이 같은 현금을 써서 음수 현금이 되는 일을 막는다.
- 체결 성공 시 주문 상태 갱신과 원장 추가는 하나의 DB 트랜잭션으로 끝낸다. 부분 기록이 남으면 안 된다.

### 2. 저장된 가격 조회

- `backend/app/market_data.py`의 저장 가격 접근 방식을 최소 확장해 아래 두 조회를 제공하거나 동등한 내부 함수를 둔다.
  - 주문 결정일에 저장된 비조정 일봉이 있는지 확인
  - 결정일보다 뒤인 가장 이른 비조정 일봉의 시가·거래일·출처·수집 실행 식별자 조회
- 두 조회는 PostgreSQL의 `daily_prices`만 읽는다. `collect_daily_prices`, `fetch_ohlcv`, pykrx, HTTP 요청을 호출하지 않는다.
- 가격 행이 없거나 조정 가격뿐이면 안전하게 사용할 수 없음을 명시하고 주문·현금 데이터를 바꾸지 않는다.

### 3. API

모든 응답은 실제 돈·계좌·주문과 무관한 가상 학습 기능임을 명시한다. 오류·응답·로그에 DB 연결 문자열, 비밀값, 환경변수 값 전체를 넣지 않는다.

- `POST /virtual-orders`
  - 본문: `ticker`(숫자 6자리), `quantity`(양수 정수), `decision_trade_date`(ISO 날짜)
  - 가상계좌가 없으면 404, 형식 오류는 422다.
  - 결정일의 비조정 일봉이 없으면 외부 요청 없이 409로 실패한다.
  - 성공하면 `pending` 매수 주문을 만든다. 현금 원장은 추가하지 않는다.
- `POST /virtual-orders/{order_id}/execute`
  - 지정한 `pending` 주문 한 건만 수동 체결 시도한다.
  - 다음 거래일 시가가 없으면 주문을 바꾸지 않고 409를 반환한다.
  - 가격이 있고 현금이 충분하면 `filled`와 음수 `buy_execution` 현금 원장 한 행을 원자적으로 기록한다.
  - 가격이 있고 현금이 부족하면 `rejected_insufficient_cash`만 기록한다.
  - 이미 `filled` 또는 `rejected_insufficient_cash`인 주문은 결과를 그대로 반환하며 원장을 더 만들지 않는다.
- `GET /virtual-orders`
  - 주문을 `created_at ASC, id ASC`로 반환한다. 외부 수집·체결·상태 변경을 시작하지 않는다.

### 4. 테스트와 문서

- 주문 입력 검증, 계좌 없음, 결정일 가격 없음, 주문 생성 시 현금 불변을 테스트한다.
- 다음 거래일 선택이 반드시 `decision_trade_date`보다 큰 가장 이른 날짜인지, 같은 날 종가·시가를 쓰지 않는지 테스트한다.
- 슬리피지·수수료 올림 규칙, 성공 체결의 음수 현금 원장 한 건, 체결 API 반복 호출의 중복 원장 방지를 테스트한다.
- 현금 부족 종료, 다음 거래일 가격 부재 시 pending 유지, 주문·원장·현금이 부분 기록되지 않는 실패 경로를 테스트한다.
- 동시 실행을 직접 재현하지 못하면 통과로 쓰지 않는다. 다만 DB 행 잠금과 유일 제약을 코드·테스트 근거에 명시한다.
- 기존 health, T-002 시장 데이터, T-003 가상계좌 테스트가 계속 통과하는지 확인한다. 자동 테스트는 pykrx·실제 증권사·실제 계좌에 요청을 보내지 않는다.
- README에 주문 생성·수동 체결 순서, 다음 거래일 시가 규칙, 비용 가정, 매수 전용·대기 주문 현금 미예약·실제 투자 아님을 기록한다.

- 실제 증권 계좌·실제 주문·자동매매·투자 조언
- 실시간·장중 가격, 가격 수집 변경, pykrx 외 다른 제공처, 자동 수집·스케줄러·작업 큐
- frontend, 사용자 로그인·다중 사용자·권한, Notion 내보내기, 정책 변경 API

## 완료 기준

1. 가상계좌가 있는 단일 로컬 사용자만 비조정 저장 일봉을 근거로 `pending` 매수 주문을 만들 수 있고, 주문 생성은 현금을 바꾸지 않는다.
2. 체결은 결정일보다 엄격히 뒤인 첫 저장 거래일의 시가만 사용하며, 같은 날 가격·종가·외부 수집을 사용하지 않는다.
3. 체결 주문에는 가격 출처·비조정 여부·수집 실행 식별자와 계산된 기준가·체결가·총액·수수료가 남는다.
4. T-003 계좌 스냅샷의 슬리피지·매수 수수료를 정수 금액과 명시적 올림 규칙으로 적용한다.
5. 충분한 현금의 체결은 주문 상태와 음수 `buy_execution` 현금 원장을 하나의 트랜잭션으로 정확히 한 번 기록한다.
6. 현금 부족은 원장 없이 종료 상태로 남고, 다음 거래일 가격 부재는 `pending`을 유지한다. 어느 경우도 현금이 음수가 되지 않는다.
7. 반복 체결 호출은 이미 종료된 주문의 결과만 반환하며 현금 원장을 중복하지 않는다.
8. 매도·취소·포지션·손익·실제 주문·자동 실행·frontend·Notion 기능이 추가되지 않는다.
9. 기존 테스트를 포함한 backend 자동 테스트 결과와, 가능하면 실제 PostgreSQL 확인 결과를 구분해 남긴다.
10. README와 `docs/handoffs/T-004-claude-handoff.md`에 사용법·검증 증거·가정·제한이 기록된다.
