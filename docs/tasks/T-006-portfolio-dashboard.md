# T-006 가상 포트폴리오 계산과 읽기 전용 대시보드

| 항목 | 내용 |
|---|---|
| 작업 ID | T-006 |
| 상태 | Claude 구현 대기 |
| 작업 브랜치 | `codex/portfolio` |
| 구현 | Claude Code |
| 기획·검증 | Codex |
| 선행 작업 | T-002, T-003, T-004, T-005 |

## 목표

이미 체결된 가상 **매수** 주문과 DB에 저장된 비조정 일봉만 재사용하여 현재 보유 수량과 평가 결과를 계산한다. 계산 결과를 Django Template의 읽기 전용 대시보드에 명확하고 반응형으로 표시한다.

이 화면은 투자 판단을 복기하는 학습용 장부다. 실제 계좌·실제 주문·실시간 가격을 암시하거나 실행해서는 안 된다.

## 범위와 제외

### 이번 작업에 포함

- `filled` 상태인 `VirtualBuyOrder`를 종목별로 합산한 보유 수량·매수 원가·평가 결과 계산
- `DailyPrice`의 저장된 **비조정 종가**를 사용한 종목별·계좌 전체 평가
- 기존 `GET /` Django Template 대시보드의 정적 CSS·semantic HTML 개선
- 데이터 기준일과 가격 출처, 계산 불가 사유의 명시적 표시

### 이번 작업에서 제외

- 매도, 실현 손익, 실제 주문·실제 계좌, 자동매매
- 실시간 가격, 가격 자동 수집, pykrx 호출, 스케줄러·큐
- 주문 입력·계좌 초기화·데이터 수집을 위한 화면 form 또는 버튼
- Notion API, 인증·다중 사용자, 차트·포트폴리오 이력 저장
- 새 frontend framework, JavaScript framework, CSS library, icon library, 외부 폰트
- 새 공개 JSON API 또는 DB 테이블·migration

`virtual_positions` 같은 저장 포지션 테이블은 만들지 않는다. 매도 기능 전까지는 체결 매수 주문을 합산하는 방식이 더 단순하고 원장과도 일관된다. 매도·실현손익 작업을 시작할 때만 보유 수량 저장 모델이 필요한지 다시 판단한다.

## 데이터와 계산 규칙

### 입력 범위

- 계좌는 기존 단일 `VirtualAccount` 한 개만 사용한다.
- 보유 종목은 해당 계좌의 `status="filled"` 매수 주문만으로 구성한다. `pending`, `rejected_insufficient_cash` 주문은 보유 수량·원가·평가에 포함하지 않는다.
- 체결 주문의 `quantity`, `gross_amount_krw`, `fee_krw`, `execution_trade_date`가 비어 있거나 유효하지 않으면 임의로 0으로 보정하지 않는다. 해당 포트폴리오를 `calculation_unavailable`로 표시하고 안전한 안내를 남긴다.
- 가격은 `DailyPrice(adjusted=False)`의 `close_price`만 읽는다. 체결가·당일 시가·조정주가·외부 API 응답·추정 가격은 평가에 쓰지 않는다.

### 공통 평가 기준일

서로 다른 날짜의 가격을 한 계좌 평가에 섞지 않는다.

1. 보유 종목마다 저장된 비조정 일봉의 거래일 집합을 구한다.
2. 모든 보유 종목에 공통으로 있는 거래일 중, 모든 체결 주문의 가장 늦은 `execution_trade_date`와 같거나 뒤인 날짜만 후보로 삼는다.
3. 그 후보 중 가장 늦은 날짜를 `valuation_trade_date`로 선택한다.
4. 선택 날짜의 각 종목 `close_price`를 평가 기준가로 사용한다.

공통 후보가 없거나 필요한 가격 행이 없으면 외부 수집·보간·이전 가격 대체를 하지 않는다. 종목별 보유 수량과 매수 원가는 표시할 수 있어도 평가금액·평가손익·수익률·계좌 총자산은 `계산 불가`로 표시하고, 각 보유 종목의 일봉을 겹치는 기간까지 수동 수집해야 한다는 사유를 표시한다.

보유 종목이 하나도 없으면 가격 기준일 없이 `보유 종목 없음` 상태로 표시한다. 이때 평가금액은 0원, 총자산은 가용 현금, 총 평가손익은 `가용 현금 - 최초 가상 현금`으로 계산할 수 있다. T-006 범위의 정상 흐름에서는 이 값이 0원이다.

### 금액 공식

모든 KRW 금액은 기존 정수 필드를 그대로 사용한다. 수익률 중간 계산에는 `Decimal`을 사용하고 binary float를 사용하지 않는다.

| 항목 | 공식 |
|---|---|
| 보유 수량 | 같은 종목의 `filled.quantity` 합계 |
| 매수 원가 | 같은 종목의 `filled.gross_amount_krw + filled.fee_krw` 합계 |
| 평가금액 | `보유 수량 × valuation_close_price_krw` |
| 평가손익 | `평가금액 - 매수 원가` |
| 종목 수익률 | `평가손익 ÷ 매수 원가 × 100` |
| 총 평가금액 | 평가 가능한 종목 평가금액의 합계 |
| 총자산 | `가용 현금 + 총 평가금액` |
| 총 평가손익 | `총자산 - 최초 가상 현금` |
| 총 수익률 | `총 평가손익 ÷ 최초 가상 현금 × 100` |

- 수익률은 소수 둘째 자리까지 반올림해 표시한다. 서비스·template 경계에서는 고정 소수점 문자열 또는 `Decimal`을 사용하며 JSON float를 새로 만들지 않는다.
- 매도는 없으므로 매도 수수료·매도 세금은 이 계산에 적용하지 않는다. 매수 수수료는 이미 매수 원가에 포함된다.
- 각 손익·수익률은 `positive`, `negative`, `neutral`의 텍스트 상태도 함께 제공한다. 색상은 보조 수단일 뿐이며 수익·손실·변동 없음 텍스트를 반드시 보인다.

## 구현 설계

### 서비스 계층

- 계산은 `backend/trading/portfolio.py` 같은 작은 읽기 전용 모듈에 둔다. view 또는 template에서 ORM 집계·금액 공식을 중복 구현하지 않는다.
- 기존 `accounts.available_cash(account)`을 재사용한다.
- 계산 함수는 읽기만 한다. 계좌 초기화, 주문 생성·체결, 원장 추가, 일봉 수집, pykrx 호출, DB schema 변경을 시작하면 안 된다.
- `GET /`만 이 모듈을 호출한다. T-006에서는 `/portfolio` 같은 새 공개 API를 추가하지 않는다.
- DB 연결 실패는 기존 대시보드처럼 쓰기 없이 안내 상태로 처리한다. 정상 데이터가 없거나 평가가 불가능한 상태와 DB 연결 실패를 구별한다.

### Django Template과 static CSS

- 기존 `backend/templates/trading/dashboard.html`을 유지·개선하고, Django app static 경로에 CSS 파일 한 개를 추가한다. Template에서 `{% load static %}`으로 CSS를 연결한다.
- 현재 설정에 없으므로 Django 기본 제공 `django.contrib.staticfiles`와 `STATIC_URL`을 최소로 설정해 개발 Compose의 static CSS가 실제로 제공되게 한다. 이는 Django 내장 기능이며 새 패키지가 아니다. production 배포용 CDN·storage·`STATIC_ROOT` 설계는 이번 범위가 아니다.
- JavaScript, CDN, 외부 이미지·폰트, Bootstrap·Tailwind·React·다른 CSS 라이브러리를 추가하지 않는다.
- 한글 OS/browser system font stack을 사용한다. 네트워크 폰트를 가져오지 않는다.
- 디자인 방향은 광고형 금융 서비스가 아니라 **학습용 투자 장부**다. 시원한 밝은 배경, 신뢰를 주는 navy/blue, 수익 보조색 emerald, 손실 보조색 red 계열의 접근 가능한 대비를 사용한다. 큰 hero, CTA, 영상, 과도한 glass/blur·그림자·애니메이션은 쓰지 않는다.
- CSS custom property로 색·간격·테두리 토큰을 한 곳에 둔다. 색상값을 component마다 반복하지 않는다.
- semantic HTML을 사용한다: `header`, `main`, `section`, 논리적 heading, `table`, `caption`, `th scope`, 의미 있는 empty/error 안내. 숫자에만 의존하지 않고 단위(KRW, 주, %)와 기준일을 함께 표시한다.
- 대시보드는 최소한 아래 순서로 구성한다.
  1. 주몽 제목, 가상 학습 서비스·읽기 전용 안내
  2. 평가 기준일·가격 출처 또는 평가 불가 사유
  3. 총자산, 가용 현금, 평가금액, 총 평가손익·총 수익률 요약
  4. 보유 종목 표: 종목, 보유 수량, 매수 원가, 기준 종가와 출처, 평가금액, 평가손익, 수익률
  5. 기존 최근 매수 주문 표(최신순 최대 20건)
- 화면 폭 375px, 768px, 1024px, 1440px에서 내용을 확인한다. 좁은 화면에서 보유 종목·최근 주문 표는 각 행의 label을 보존한 stacked layout으로 바꾸며, 가로 스크롤에 의존하지 않는다.
- keyboard focus가 명확해야 한다. 링크·버튼이 생기지 않는 읽기 전용 화면이라도 브라우저 기본 focus를 제거하지 않는다. 움직임을 추가하지 않는다.

## 완료 기준

1. `filled` 매수 주문만 이용해 종목별 보유 수량과 매수 원가를 계산하며, pending·거절 주문은 제외한다.
2. 모든 보유 종목에 공통인 가장 최신의 저장 비조정 종가와 그 기준일만 사용한다. 기준일은 모든 체결일보다 빠르면 안 된다.
3. 평가금액·평가손익·종목 수익률, 가용 현금·총자산·총 평가손익·총 수익률이 정수/`Decimal` 규칙으로 정확히 계산된다. 매수 수수료는 원가에 포함된다.
4. 가격 공통일이 없거나 체결 데이터가 불완전하면 외부 요청·추정·0 보정 없이 `계산 불가`와 안전한 사유를 보인다.
5. `GET /`는 읽기 전용이고 계산 결과, 기준일·출처, 보유 종목, 최근 주문을 Django Template으로 표시한다. 보유 종목이 없고 DB/계좌가 없는 상태도 구별해 안내한다.
6. Django static CSS와 semantic HTML만 사용한다. 외부 font/CSS/JS와 새 frontend framework·CSS library가 없다.
7. 375px부터 desktop까지 반응형이며, 모바일 표가 가로 스크롤에 의존하지 않고 색상만으로 수익·손실을 전달하지 않는다.
8. 새 migration·새 DB 테이블·새 공개 API·자동 수집·주문 입력 form을 추가하지 않는다. 기존 JSON API의 경로·응답은 바꾸지 않는다.
9. 기존 테스트를 깨뜨리지 않고, 아래 T-006 테스트를 추가한다.
10. `docs/handoffs/T-006-claude-handoff.md`에 변경 파일·요구사항별 구현 위치·명령/결과·테스트 범위·가정/제한을 남긴다.

## 최소 테스트 기준

- 단일·복수 종목의 filled 매수 주문, 매수 수수료 포함 원가, 종목별/총 손익·수익률을 정확히 검증한다.
- pending·현금 부족 거절 주문이 보유 수량과 평가에 포함되지 않음을 검증한다.
- 최신 공통 기준일 선택, 체결일보다 이른 공통 날짜 배제, 공통 기준일 부재의 `계산 불가`를 검증한다.
- 포트폴리오 계산과 `GET /`가 `DailyPrice` 외부 수집 함수·주문 체결·원장 쓰기를 호출하지 않음을 검증한다.
- 계좌 없음, 보유 종목 없음, DB 오류 또는 불완전 체결 데이터를 안전하게 표시하는 template 응답을 검증한다.
- `manage.py check`, `manage.py makemigrations --check --dry-run`, 전체 Django test runner를 실행한다. 실제 DB 확인·브라우저 화면 확인을 했다면 자동 테스트와 분리해 기록한다.

## 확인이 필요한 경우

화면 구성, 표시 문구, 평가 기준일, 기존 데이터의 불일치 등 이 문서에서 결정하지 않은 사항이 구현에 영향을 주면 추측하지 않는다. Claude Code는 구현을 멈추고 Codex에 질문한다. Codex는 제품 방향을 바꾸는 선택이라면 사용자에게 확인한다.
